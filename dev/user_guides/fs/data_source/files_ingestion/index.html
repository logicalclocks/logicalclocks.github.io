    Copy files from S3, GCS, ADLS, SFTP or Google Drive into a dataset#

    Introduction#

    An S3, GCS or ADLS data source can do more than back external feature groups over tabular files. It can also copy the files under a prefix of its bucket or container, whatever their format, into a dataset of the project, either once or on a schedule. An SFTP or Google Drive data source exists only for this, and copies the files under a path of the server or a folder of the Drive the same way. This is the files mode of the dltHub ingestion job that also ingests tables into feature groups.

    Each run lists the prefix, copies the files that are new or changed, skips the ones it already has, and writes a small CSV audit file of what it changed, so downstream jobs can process only what changed. Optionally, a run also deletes from the dataset the files that disappeared from the source, and keeps a feature group with one row per file.

    Data only flows from the source into Hopsworks. Changes made in the dataset are never written back to the bucket.

    Typical uses are document corpora for retrieval, agents and unstructured data pipelines, where the files are read from the dataset through the HopsFS mount of a job, a terminal or an app. Tabular files that should become feature groups are better served by an external feature group over the path, or by the table ingestion flow; see Limitations.

    Prerequisites#

    Data source#

    A data source of type S3, GCS, ADLS, SFTP or Google Drive in the project's feature store, with credentials that can list and read the prefix. Create it as described in the S3, GCS, ADLS, SFTP or Google Drive guide. Other data source types are not supported; see Limitations.

    An S3 data source that authenticates with an IAM role must have a role mapping an administrator created with AWS Role chaining; a data source without one is refused when the job is created. Hopsworks assumes the role when it starts the job and hands the job temporary credentials that live for dlt_files_credentials_duration_seconds, an hour by default. A run longer than that fails at the first request made with the expired credentials, so for a long first copy an administrator raises the setting, and before that the maximum session duration of the role, which must allow it. Access key and secret, service account key file, service principal, SFTP password and SFTP private key credentials have no such limit.

    Role#

    Only data owners of the project can create, change or run a files ingestion job, because the copy widens access: every member who can read the dataset can read every copied file, whatever permissions the objects carry in the bucket. A scheduled run executes as the user who created the job, so when that user leaves the project, another data owner takes the job over by editing it.

    Cluster version and environment#

    Files ingestion is available from Hopsworks 5.3.0. The job runs in the dlthub-ingestion-pipeline environment, whose image ships with the cluster; the files mode needs the image of the same release as the backend, so a cluster that pins an older image cannot run it. The Python client and the hops CLI need the same version or later.

    Cluster settings#

    Variable Default Meaning
    data_source_audit_retention_days 7 Days of audit files kept per dataset. 0 keeps them forever.
    dlt_files_credentials_duration_seconds 3600 Lifetime in seconds of the temporary credentials a run gets from an IAM-role S3 data source; the role's maximum session duration must allow it, and a longer run fails at the first expired request.
    dlt_files_listing_timeout_seconds 3600 Seconds a run waits for the listing of the prefix; see How a run works.

    Creation in the UI#

    Step 1: Open the data source#

    Head to the Data Sources view in Hopsworks and open the data source, or create it and continue from its last step. Click Next to open the second step of the wizard.

    Step 2: Choose Copy files into a dataset#

    The second step offers two ways to use the data source: External feature group over a path, which keeps the files where they are, and Copy files into a dataset, which this guide covers. For an ADLS, SFTP or Google Drive data source only the second is offered, since those types back no feature groups.

    1. Prefix: the path inside the bucket or container whose files are copied, for example handbook/2026/. It is relative to the root of the bucket or container; the path set on an S3 data source is not applied, so repeat it in the prefix when the files live under it. For SFTP it is relative to the root path of the data source, and for Google Drive it is a path of folder names below the shared folder, so a run lists sftp://<host>:<port><root path>/<prefix> or gdrive://<folder ID>/<prefix>. A prefix is a folder, not the start of a key: the job lists under <prefix>/, so handbook selects handbook/a.pdf but not handbook-old/a.pdf. Click Browse to pick it from a listing of the bucket; each level lists its folders and files, with their size and modification time. Browsing is not available for ADLS, SFTP and Google Drive, so type the prefix there. An empty prefix copies the whole bucket, root path or folder; see How a run works before doing that on a large one.
    2. Include and Exclude: glob patterns, one per line, matched against the path of each file relative to the prefix, not to the bucket. With prefix handbook/, write **/*.pdf, not handbook/**/*.pdf. ** matches across folders, so **/*.pdf selects every PDF under the prefix and **/~$* excludes Office lock files. A file is copied when it matches at least one include pattern, or all of them when there is none, and no exclude pattern.
    3. Dataset: a new dataset in the project root, or an existing one. A new dataset is created editable by data owners only, and an existing one is accepted only with that permission, since every run writes into it as a data owner. The platform datasets Logs, Resources, Jupyter, Models, and the training-datasets and feature-store datasets cannot be targets. A dataset can be the target of at most one files ingestion job across all data sources of the project; choosing one that another job already copies into is refused.
    4. Mirror deletions: also delete from the dataset the files that are no longer under the prefix; see Mirroring deletions. Off by default, so a plain run only adds and updates.
    5. Index the files in a feature group: keep a feature group with one row per file; see The file index. Feature group names it; empty means files_<dataset>.
    6. Maximum file size in MB; larger files are skipped and reported. Empty or 0 copies every file.
    7. Schedule: an optional schedule for recurring runs, as for any scheduled job: a Quartz cron expression in UTC, seconds first, so 0 0 2 ? * * runs daily at 02:00.
    8. Memory and CPU cores of the job, 2048 MB and 1 core by default; downloads wait on the network most of the time, so memory matters more than cores.
    9. Under Advanced:
      • Files per page: how many objects a listing request returns, 100 by default.
      • Parallel downloads: how many files are downloaded at the same time, 4 by default and at most 16; see Parallel downloads.
      • Fail on first error: stop the run at the first file that fails instead of continuing with the others.
      • Transform script: an optional Python file of the project that runs on every file before it is stored; see Transforming files. Keep the original files, shown once a script is chosen, also stores each file as it is in the source.
      • Job name: <data source>_<dataset>_files by default, with every character outside letters, digits and underscore replaced by _.
      • Alerts: an alert receiver notified when a run fails.

    Click Create to create the job, the dataset if it is new, and the index feature group if indexing is on. The job is also started unless you turn Start the job after creation off.

    The job page#

    The job appears in the Jobs view like any other ingestion job, and its page shows the data source, prefix, patterns and dataset it copies into. Edit changes the prefix, patterns, mirroring, indexing, size cap, transform script, schedule and resources; the data source and the dataset of a job cannot change, so create another job to copy into a different dataset.

    Each execution row shows the counters of the run: files listed (after the include and exclude patterns), copied, updated, skipped as unchanged, deleted, failed, oversized and unsupported, and the bytes copied. A run of a job with a transform script also shows the files it transformed and the files the script dropped. The Audit link of a run that changed something opens its audit CSV in the file browser; see State and audit files. The execution logs show every file the run touched and the error of each file that failed.

    Deleting the job#

    Deleting the job removes its schedule, its credentials in the cluster and its state directory, and keeps the dataset and the index feature group by default. The delete dialog offers Also delete the dataset and Also delete the index feature group. The index is only deleted when it is the feature group the job created, so a feature group that existed before the job is never removed. A data source that still has files ingestion jobs cannot be deleted; delete the jobs first.

    Using the Python client#

    ingest_files on an S3, GCS, ADLS, SFTP or Google Drive data source creates the job and returns it; other data source types raise.

    import hopsworks


project = hopsworks.login()
fs = project.get_feature_store()

s3 = fs.get_data_source("acme_docs").storage_connector

job = s3.ingest_files(
    dataset="acme_docs_handbook",  # existing (owned) or new
    prefix="handbook/2026/",  # a folder, from the bucket root; relative to it:
    include=["**/*.pdf", "**/*.docx"],
    exclude=["**/~$*"],
    mirror_deletions=False,
    index=False,  # True -> files_<dataset>; or a feature group name
    max_file_size_mb=None,  # None or 0 -> no cap
    schedule=None,  # Quartz cron in UTC, e.g. "0 0 2 ? * *" for daily at 02:00
    resources=None,  # {"cores": 1, "memory": 2048, "gpus": 0}
    name=None,  # job name, default "<data source>_<dataset>_files"
    fail_on_first_error=False,
    files_per_page=100,
    copy_workers=4,  # files downloaded at the same time, 1 to 16
    transform_script=None,  # e.g. "Resources/transform.py", see Transforming files
    keep_original=False,  # with a script: also store the file as it is in the source
)

execution = job.run(await_termination=True)
execution.files_progress  # counters of the run, None until the run wrote them
job.last_stats  # the same for the latest execution

job.job  # the hopsworks Job
job.name, job.dataset_name, job.prefix, job.index_feature_group

job = job.update(
    prefix="handbook/",
    include=["**/*.pdf"],
    mirror_deletions=True,
    index=True,
    max_file_size_mb=500,
)

s3.get_files_ingestion_jobs()  # the files ingestion jobs of this data source

job.delete(delete_files=False, delete_index=False)

    files_progress and last_stats return the stats of the run as a dictionary with the keys of the stats file described in State and audit files, plus datasetName, connectorName, prefix and auditPath, the absolute HopsFS path of the audit file. prefix is a folder relative to the root of the bucket or container, to the SFTP root path or to the Drive folder, as in the UI, and the patterns are relative to the prefix. update re-saves the job; a job's data source and dataset cannot change. index accepts a feature group name only while the job had no index; afterwards turning it on uses the name chosen then. transform_script and keep_original can be given to update too; transform_script=None removes the transform.

    Using the CLI#

    hops datasource ingest-files acme_docs --dataset acme_docs_handbook \
  --prefix handbook/2026/ --include "**/*.pdf" --include "**/*.docx" \
  --exclude "**/~$*" --cron "0 0 2 ? * *"
hops datasource ingest-files acme_docs --dataset acme_docs_handbook \
  --prefix handbook/ --mirror-deletions --index --max-file-size-mb 500 --no-run

    The command creates the job, prints its name and, unless --no-run, starts a run and prints its execution id. --include and --exclude repeat; --index names the feature group files_<dataset> and --index-name chooses another name; --name sets the job name. --copy-workers sets how many files are downloaded at the same time. --transform-script Resources/transform.py runs a transform script on every file, and --keep-original with it also stores the files as they are in the source. hops datasource files-jobs acme_docs lists the files ingestion jobs of the data source. Runs, schedules, logs and deletion of the job are managed with the hops job commands, as for any job.

    How a run works#

    The job runs as a Kubernetes pod of the dlthub-ingestion-pipeline environment, with the data source's credentials in a Secret and the job's configuration in a ConfigMap that are rewritten at every start, so a credential changed on the data source is used by the next run. The dataset and the state directory are reached through the pod's HopsFS mount. A run goes through these steps.

    1. Lease. The run takes a lease on the dataset, lease.json in the state directory, and refreshes it every minute. A run that finds a lease refreshed within the last five minutes by another execution exits without copying anything, as a success, with another run is active in its log; this is what happens when a schedule fires while the previous run is still copying. A lease older than five minutes is taken over, so a killed run does not block the next one.
    2. Listing. The run lists every object under the prefix, in pages of Files per page, and applies the include and exclude patterns. The listing is full every run, with no incremental listing, so a run over a prefix with millions of objects spends most of its time listing; narrow the prefix, or split it across jobs, for very large buckets. The run waits dlt_files_listing_timeout_seconds, an hour by default, for the listing; the timeout bounds the listing only, not the copies. A listing that exceeds it fails the run with an incomplete listing, listingComplete false in the stats, and deletions are never mirrored from one.
    3. Skip or copy. Each listed file is compared with its row in the manifest of the previous runs. A file whose copy is in the dataset is skipped, and counted as skipped, when its size and entity tag match the previous copy, where the data source provides one: the ETag of S3, the etag of GCS and ADLS, and the version of Google Drive. Otherwise, as on SFTP, it is skipped when its size and modification date match, so a file changed without a change of either is only copied again after it is deleted from the dataset. A file over the size cap is counted as oversized, listed in the audit file, and not copied until it shrinks or the cap is raised. A file that cannot be copied at all, such as a Google-native document, a symbolic link on an SFTP server or a Google Drive file whose name contains a slash, is counted as unsupported, listed in the audit file and left out; it does not fail the run. An archived S3 object, in the GLACIER or DEEP_ARCHIVE storage class, is reported as unsupported the same way; restore it in S3 before a run can copy it. A copy made before a file became unsupported stays in the dataset, also when deletions are mirrored, for as long as the file is still in the source. Any other file is downloaded, several at a time, into a temporary file outside the dataset and renamed into place once complete, so readers of the dataset never see a partial file; it is counted as copied when new and updated when it replaced an earlier copy. When the data source provides a checksum of the file, the download is verified against it before the rename: GCS, Google Drive, S3 objects uploaded in a single part, and ADLS files that have a content MD5 set. The copy keeps the path relative to the prefix, so handbook/2026/a/b.pdf under prefix handbook/2026/ lands at <dataset>/a/b.pdf.
    4. Failures. A file that cannot be downloaded or written, or whose download does not match the checksum of the data source, is counted as failed, logged with its error, and the run continues with the next file unless Fail on first error is on. The previous copy of a failed file, if any, stays in place and in the manifest, and the file is retried on the next run. A run that cannot list the prefix, reach the dataset or write its state fails outright.
    5. Mirroring and indexing, when turned on; see the next sections.
    6. Stats and audit. The run writes its stats file and, when it changed something, its audit file, then releases the lease.

    The outcome of a run is its status in the stats file and the state of its execution:

    Status Exit code Execution Meaning
    ok 0 FINISHED Every listed file is in the dataset, copied or unchanged; oversized files are reported but do not fail the run.
    partial 2 FAILED Some files failed, or the prefix listed nothing while the dataset holds copies; the successful copies are kept and the failed ones are retried on the next run.
    failed 1 FAILED The run stopped on an error, named in error and in the logs; with Fail on first error, that of the first file.

    A partial run fails its execution so that the alert receiver is notified and the execution row shows it; the dataset still holds every file that was copied.

    A run that is killed, or that loses its credentials when an IAM role session expires, leaves no partial file in the dataset, since copies are renamed into place only when complete, and leaves its lease to expire. The manifest is written whole at the end of a run, so the files such a run copied are compared by size and modification date again on the next run and found unchanged.

    Transforming files#

    By default a file is stored exactly as it is in the data source. A job with a transform script runs your Python code on every file after it is downloaded and verified and before anything of it is in the dataset, for example to redact text, to convert a format or an encoding, to decompress, or to leave out files by their content.

    The script#

    The script is a .py file in the project, uploaded like any other file, for example to Resources. It defines one subclass of HopsFileTransformer:

    # Resources/transform.py
import os

from dlt.destinations.impl.hopsworks_fg import HopsFileTransformer


class RedactText(HopsFileTransformer):
    def transform(self, path: str, context: dict) -> str | None:
        if context["file_name"].startswith("~"):
            return None  # store nothing of this file
        name = os.path.splitext(context["file_name"])[0] + ".txt"
        out = os.path.join(context["work_dir"], name)
        with open(path, errors="replace") as src, open(out, "w") as dst:
            dst.write(src.read().replace("CONFIDENTIAL", "***"))
        return out

    path is the downloaded file on the local disk of the job. The method returns one of:

    • the path of a new file written under context["work_dir"]; its name becomes the name of the stored file, so a transform can change the extension;
    • path itself, when the file was changed in place or is to be stored as it is;
    • None, to store no output for this file.

    context describes the file:

    Key Content
    relative_path, file_name the path relative to the prefix, and its last part
    source_url the object in the data source
    size_bytes, modified_at, mime_type as listed by the data source
    etag, source_id, source_content_type, created_at the source metadata of the file index, when the data source provides it
    connector, source_type, dataset, job_name, execution_id the job and the run
    keep_original whether the job keeps the original files
    work_dir a scratch directory of this file, removed after the file is stored

    The base class is imported from the job's environment, so the import fails in a notebook or a terminal; that is expected, since the script is only ever loaded by the job. A library the script imports must be installed in the environment the job runs in: clone dlthub-ingestion-pipeline, install it there and choose the clone as the job's environment.

    Where the files land#

    Original file Output of the script
    Keep the original files off (the default) not stored <dataset>/<folder of the file>/<returned name>, which is the path of the source file when the name is unchanged
    Keep the original files on <dataset>/<relative path>, as without a script <dataset>/_transformed/<folder of the file>/<returned name>

    So with the script above, a/report.docx is stored as a/report.txt, or, with the originals kept, as a/report.docx and _transformed/a/report.txt.

    When the originals are kept, path is the stored original itself: read it, and write the output under work_dir. Returning path or None then stores no separate output. When they are not kept, a file the script returns None for is counted as dropped and nothing of it is stored; it is not downloaded again until it changes in the source.

    Two source files must not produce the same stored path, as a.docx and a.pdf both would with the script above. The second one fails with output path ... is already used by ...; give such outputs different names, for example by keeping the source extension in the name.

    Changes and failures#

    • A file changed in the source is downloaded and transformed again, like a plain copy; the skip rule compares the source file, not the output.
    • A changed script, whether another file is chosen or the same file is edited, processes every file again on the next run. With the originals kept, the run reads them from the dataset and downloads nothing. Without them, every file is downloaded again.
    • Removing the script turns the copies back into plain ones on the next run and deletes the outputs.
    • Turning Keep the original files on downloads the files again to store the originals. Turning it off leaves the originals that are already stored where they are.
    • A script that raises fails that file only, with transform failed: <error> among the failed files, and the run continues and ends as partial. Without originals nothing of the file is stored; with originals the original is stored and the next run transforms it again without a download.
    • A script that cannot be loaded, because the file is missing, does not import, or defines no HopsFileTransformer, fails the run before it lists anything, and the dataset is left as it was.

    Mirroring deletions removes the original and the output of a file that is gone from the source.

    The script runs once per file, one file at a time, inside the copy; parallel downloads fetch the files ahead of it, they do not run it in parallel. Keep it to work that is cheap per file; parsing documents, chunking and embedding are better done by a separate job that reads the file index, which keeps the copy fast and repeatable.

    Parallel downloads#

    A run downloads 4 files at the same time by default; Parallel downloads in the UI, copy_workers in the Python client and --copy-workers in the CLI set a number from 1 to 16. Only the downloads run in parallel. Deciding whether a file is skipped, running the transform script, moving the file into the dataset and recording it all happen in the order of the listing, one file at a time, so a run stores the same files with any setting.

    Situation Setting
    Many small files Raise it; the time per file is mostly the round trip to the source.
    A few large files Leave it; the network or the source's bandwidth is the limit, not the number of downloads.
    The source throttles or answers with rate-limit errors, as Google Drive does under load Lower it.
    An SFTP server that limits the sessions of one user Lower it, or set 1.

    On SFTP and Google Drive every parallel download uses its own connection to the source, in addition to the one that lists the files. When the source refuses an additional connection the job logs a warning and downloads those files one at a time over the connection it has; no file fails because of it. Downloaded files wait in the job's temporary directory until their turn, at most twice the setting at any time, and count towards the project's storage quota while they wait.

    Mirroring deletions#

    With Mirror deletions on, a run that completed its listing without any failed file deletes from the dataset every file whose source object is gone from the prefix or no longer matches the patterns, and counts them as deleted. Empty folders left behind are removed too.

    Deletions are skipped, and deletionsSkipped is set in the stats, whenever the run cannot be sure the file is really gone:

    • the listing was incomplete, because it timed out or failed part way;
    • any file failed to copy in this run, since a listing problem and a copy problem can have the same cause;
    • the listing was complete but empty while the previous run had copied files. The run then ends as partial with the error that the prefix listed nothing, so a prefix typo or a moved folder cannot empty the dataset. Fix the prefix, or empty the dataset by hand when the source is really empty.

    The next run that lists and copies cleanly performs the deletions. A run with mirroring off never deletes, so a file removed from the prefix stays in the dataset until mirroring is turned on or a data owner deletes it.

    Mirroring only touches files the job copied, that is, files with a row in the manifest. Files that a data owner placed in the dataset by other means are left alone, but a file with the same relative path as a source object is overwritten by it.

    State and audit files#

    The job keeps its state in the project at:

    DataSources/<data source>/files/<dataset>/
    File Written by Content
    owner.json Hopsworks, when the job is created The job that copies into this dataset: jobId, jobName, connectorId, connectorName, datasetName, createdAt. A second files job on the same dataset is refused while it exists.
    lease.json the run executionId, pod, startedAt and heartbeat of the run that holds the dataset; see How a run works.
    manifest.jsonl the run One JSON object per file in the dataset: file_id (SHA-1 of the source URL), source_url, relative_path, hopsfs_path, file_name, file_type, mime_type, size_bytes, modified_at, etag (entity tag in the data source, empty for SFTP), source_id, source_content_type, created_at, content_hash (SHA-256 of the copy), execution_id and copied_at of the run that copied it. With a transform script there is still one object per source file, with original_path and output_path naming the files stored for it, source_size_bytes, and transform_hash, the SHA-256 of the script; hopsfs_path, file_name, size_bytes and content_hash then describe the output. Replaced atomically at the end of each run.
    <execution id>_files_stats.json the run, also when it fails The outcome of the run, described below.
    audit/date=<YYYY-MM-DD>/<HHMMSS>Z_<execution id>.csv the run, when it changed something One row per changed file, described below.

    The date= directories are Hive-style partitions, so a filter on date reads only the matching days. From a Python job, with DuckDB from the python-feature-pipeline environment:

    import duckdb


changes = duckdb.sql(
    """
    SELECT date, execution_id, op, path, src_path
    FROM read_csv('/hopsfs/DataSources/acme_docs/files/acme_docs_handbook/audit/*/*.csv',
                  hive_partitioning = true,
                  columns = {'execution_id': 'BIGINT', 'op': 'VARCHAR',
                             'kind': 'VARCHAR', 'path': 'VARCHAR',
                             'src_path': 'VARCHAR'})
    WHERE date >= DATE '2026-11-01' AND op IN ('copied', 'updated')
    """
).df()

    Each run deletes the audit days older than data_source_audit_retention_days.

    The file index#

    A job with indexing on keeps version 1 of a Delta feature group, files_<dataset> by default, with one row per file in the dataset. Hopsworks creates it with the job, offline only and without statistics, with file_id as primary key and ingestion_date as partition key, and the job page links it.

    Column Content
    file_id SHA-1 of the source URL, the primary key; it stays the same as long as the object keeps its key
    connector, source_type the data source and its type, s3, gcs, adls, sftp or gdrive
    file_name, file_type the name, and its extension in lowercase
    relative_path the path relative to the prefix and to the dataset root
    hopsfs_path the copy in the dataset, /Projects/<project>/<dataset>/...
    source_url the object, as s3://, gs://, az://, sftp:// or gdrive:// URL
    mime_type, size_bytes content type, from the extension, and size in bytes
    modified_at the object's last modification time, UTC
    content_hash SHA-256 of the copy
    etag the entity tag in the data source: the ETag of S3, the etag of GCS and ADLS, the version of Google Drive; null for SFTP
    source_id the identifier of the file in the data source: the file ID of Google Drive, the generation of GCS, the version ID of ADLS
    source_content_type the content type recorded in the data source
    created_at the creation time in the data source
    original_hopsfs_path for a job with a transform script that keeps the originals: the file as it is in the source, while hopsfs_path, file_name, file_type, size_bytes and content_hash describe the output of the script; null otherwise
    execution_id, indexed_at the run that last wrote the row, and when
    ingestion_date the partition: the UTC day the file was first indexed, which is the day it was copied in, or for a file already in the dataset, the day indexing was turned on

    The table holds no file content; the file is in the dataset at hopsfs_path. A file a transform script stored nothing of has no row.

    After mirroring, each run compares the manifest with the table:

    • A file that has no row, or whose relative_path, size_bytes, modified_at or content_hash changed, is written. A new file goes into today's partition; a changed file keeps the partition of the day it was first indexed.
    • The row of a file that mirroring deleted is removed.
    • A file whose copy failed keeps its current row, or gets none, until a run copies it.

    The rows are written and deleted with delta-rs through the feature group's insert and remove_rows, so each run adds commits to the feature group's activity, and a run compacts and vacuums the table afterwards; see Delta maintenance. Indexing can be turned on for an existing job: its next run indexes every file in the manifest. Turning it off keeps the feature group. The name of an index must not be that of an existing feature group, and a job deletes only the feature group it created.

    In a terminal, the feature store is mounted at /hopsfs/featurestore/<project>_featurestore.db/, and the DuckDB CLI reads the index with its delta extension:

    duckdb -c "SELECT file_name, size_bytes, modified_at, hopsfs_path
FROM delta_scan('/hopsfs/featurestore/acme_featurestore.db/files_acme_docs_handbook_1')
WHERE file_type = 'pdf' ORDER BY modified_at DESC LIMIT 20;"

    Use delta_scan, not read_parquet over the partition directories: until a vacuum, those directories also hold the files of deleted and rewritten rows.

    Claude and the other coding agents in a terminal load the hops-files-search skill for questions about the copied files; it finds the index of a dataset and shapes the queries this way.

    Limitations#

    • Only S3, GCS, ADLS, SFTP and Google Drive data sources are supported. SharePoint, Gmail and Outlook have their own sync jobs.
    • The listing is full on every run, so a prefix with millions of objects or a very large total size is better split into several jobs with narrower prefixes.
    • A run on an IAM-role S3 data source cannot outlast dlt_files_credentials_duration_seconds.
    • Files are copied as they are, or as a transform script returns them, one output per source file. Turning tabular files into feature groups is not part of this job; use an external feature group over the path or the table ingestion flow instead.
    • Browsing the source for a prefix is not available for ADLS, SFTP and Google Drive; type the prefix.
    • One job per dataset: a dataset that one job copies into cannot be the target of another, whatever its data source.
    • The backend and the dlthub-ingestion-pipeline image must be of the same release; an older image does not know the files mode.
