    Query History#

    The semantic gateway records each metric query it runs, over every API, and Hopsworks keeps the records with the semantic project. The history is best effort: it is for seeing what ran, how long it took and why it failed, and is not an audit log. The examples use the sales semantic project of Define metrics, with id 7, in the project with id 119.

    What is recorded#

    One record per execution attempt of a query that runs, or would run, on Trino:

    Surface Recorded
    REST query and dimension-values: the Python client, the hops CLI, the query workbench in the UI, the agent tools and export runs.
    FLIGHT Statements in dbt's JDBC dialect that run a query: dbt-sl-sdk queries, ADBC and JDBC.
    BI SQL over the BI tables, which Superset charts send too.
    • Queries that fail to plan, fail on Trino, or are cancelled are recorded too, with their error.
    • Listings of metrics, dimensions and saved queries, requests for the SQL of a query, schema probes such as WHERE 1=0, and every GraphQL request are not recorded.
    • A query answered from the result cache is recorded, with the cache outcome hit.
    • A record holds no credential and no header.
    Field Value
    executionId The gateway's id of the execution, a UUID.
    user The user name of the caller.
    surface REST, FLIGHT or BI.
    buildId The build that planned the query.
    status SUCCEEDED, FAILED or CANCELLED.
    error The error of a failed or cancelled query.
    rows The rows returned.
    startedAt, finishedAt, durationMs When the query started and ended, in UTC, and how long it took.
    cache hit, miss or bypass, as the X-Semantic-Cache header of Result cache.
    servedFrom export:<export> for an answer read from an export; null otherwise.
    trinoQueryId The id of the query on Trino.
    request The metric query as the gateway normalised it, as JSON.
    sql The SQL that ran.

    The gateway sends its records to Hopsworks in batches, every 5 seconds or every 200 records. A record can be lost: when the gateway's queue is full, when a batch keeps failing after retries, when the caller's credential expires before the batch is sent, or when a gateway replica stops abruptly. The gateway's metrics port counts sent records in semantic_query_records_sent_total, and lost ones in semantic_query_records_dropped_total by reason: full, oversized, credential, failed and rejected.

    Who reads which records#

    Role in the project Reads
    Data Owner Every member's records, and one member's with the user filter.
    Data Scientist, Observer Their own records; the user filter is ignored.

    Read the history#

    hops semantic history sales --limit 3

    STARTED                           USER      SURFACE  STATUS     MS   ROWS  CACHE   QUERY                                ERROR
--------------------------------  --------  -------  ---------  ---  ----  ------  -----------------------------------  -----------------------------
2026-11-08T10:02:11.404000+00:00  meb10000  BI       SUCCEEDED  412  3     miss    revenue by customer__country         -
2026-11-08T10:01:57.120000+00:00  meb10000  REST     SUCCEEDED  9    3     hit     revenue,orders by customer__country  -
2026-11-08T10:01:30.018000+00:00  meb10000  FLIGHT   FAILED     35   -     bypass  revenue by order__state              unknown group-by order__state

    import hopsworks


project = hopsworks.login()
sales = project.get_semantic_layer_api().get_project("sales")
df = sales.query_history(limit=100, status="FAILED")
print(df[["started_at", "user", "surface", "duration_ms", "error"]])
    CLI option Python argument Meaning
    --limit limit The most records, newest first: 50 in the CLI, 100 in Python.
    --status status SUCCEEDED, FAILED or CANCELLED; repeat the option, or pass a list, for several.
    --user user A member's user name; Data Owners only.

    hops semantic history sales --json prints every field, and the list_query_history tool of the MCP server lists the records for an agent, as CSV, 20 by default. query_history returns a pandas DataFrame with one row per record, the fields in snake case, started_at and finished_at as UTC timestamps.

    In the UI, the Query history card of the semantic project's overview lists the records, newest first, with Started, User for Data Owners, Query, Surface, Status, Duration, Rows and Cache. Succeeded, Failed and Cancelled filter it, and Newer and Older page through it.

    Parameter Meaning
    limit 1 to 1000 records, 50 by default.
    cursor The nextCursor of the previous page; nextCursor is null on the last page.
    status SUCCEEDED, FAILED or CANCELLED, comma-separated.
    surface REST, FLIGHT or BI.
    user A member's user name; Data Owners only.
    from, to ISO-8601 instants on the start time; from is inclusive.

    Records come newest first. Data Owners, Data Scientists and Observers read the endpoint; an API key needs the FEATURESTORE scope. An invalid filter or cursor answers 400 SEMANTIC_LAYER_ILLEGAL_ARGUMENT.

    Retention#

    Hopsworks keeps each record for 30 days after its query started. The 30 days are a time to live in the definition of the table, hopsworks.semantic_query: RonDB stops returning a record when its time is up, and purges it. An administrator changes the time to live in RonDB, see Query history storage.

    An hourly job on Hopsworks removes the details of older records, under two cluster settings that an administrator sets in the Helm values, see Cluster variables:

    Variable Default Effect
    semantic_query_strip_details_after_days 7 Records that started earlier lose request, sql and error; who ran the query, its status, rows and duration stay until the record expires.
    semantic_query_cleaner_batch_size 1000 Records the job strips per statement.

    Deleting a semantic project, its project, or a user deletes their records. Hopsworks keeps the records in RonDB's disk tablespace, see Query history storage.
